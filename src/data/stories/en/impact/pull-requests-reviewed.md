I joined MelkRadar as a Front-End Developer, but after some time, my role changed to Front-End Technical Lead, and one of my main responsibilities became reviewing pull requests from other frontend developers on the team.

Over the roughly two years I held this responsibility, I reviewed a large number of pull requests, most of them related to the company's three main frontend projects.

We used Azure DevOps to manage our tasks, code, and pull requests. Azure had its own advantages and disadvantages, but I personally found it better than GitHub for managing and reviewing code. A lot of the information about which task a pull request came from, what changes it contained, and which part of the project it belonged to was already managed through Azure, which made the review process easier.

There were plenty of pull requests where everything looked good and I didn't need to leave any particular comments. I'd review them, and they could be merged pretty quickly. But there were also many cases where the code or final result had problems that needed to be fixed before merging.

These could be anything from differences between the implementation and the design to choosing a less suitable approach for solving a problem, not following the company's color and typography standards, issues with class and component definitions, code structure, syntax problems, and lots of other details. My job was to pay attention to all of these things and make sure the changes met our quality standards before becoming part of the project.

Whenever I found an issue, I'd leave comments on the pull request. Sometimes I'd include screenshots to show exactly where the problem was or how the result should look. Other times, I'd arrange a meeting with the developer to discuss the implementation, the reasoning behind certain changes, or a better way to approach the problem.

It was a pretty significant responsibility. If a problem made its way into the main branch or the company's product, that meant the code had passed through my review too, and I shared responsibility for it. So I had to pay attention not only to the small details, but also to the overall changes and how they could affect the project.

I really enjoyed this part of my work. It gave me the opportunity to get familiar with other developers' code and ways of thinking, discuss different approaches to solving problems, and help improve the overall quality of our projects.

After around two years, I handed over the pull request review responsibility to another team member. I onboarded them myself, explained how the process worked, what they needed to pay attention to, and which standards they should follow when reviewing code.

Both the company and I were happy with how things went during the time I held this responsibility. It was a demanding role, but a really interesting and enjoyable experience for me.
