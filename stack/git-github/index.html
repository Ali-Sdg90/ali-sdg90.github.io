Git/GitHub

Version Control & Collaboration

Used Git and GitHub extensively across personal, professional, and open-source projects for version control, collaboration, code review, project management, and CI/CD automation.

Where It Helps

  • Managing branches, commits, merges, conflicts, and collaborative development workflows
  • Reviewing pull requests and maintaining shared codebases across team and open-source projects
  • Automating testing, builds, versioning, releases, and other project workflows with GitHub Actions

Story

I first came across Git and GitHub near the end of 2022 through the CS Internship program.

At first, I found Git pretty confusing. I didn't fully understand commits, branches, where changes were going, or why I should manage my projects this way in the first place.

Little by little, I started forcing myself to put my projects on GitHub instead of keeping everything only on my laptop.

Then I found GitHub Desktop, and that changed my relationship with Git a lot. Something that had felt abstract and complicated became much easier for me to see and understand.

For around a year and a half, I mostly used Git through my own projects and CS Internship. I created branches, made commits, managed changes, and gradually became comfortable with the way Git works.

Then I joined MelkRadar, my first real company, and that was where I learned what using Git inside a professional development workflow actually looked like.

I started working with branch naming conventions, pull requests, feature branches, hotfixes, development and production branches, and the normal flow of multiple developers working across several company projects.

After some time, I became responsible for reviewing the frontend team's pull requests.

At that point, Git and pull requests became a major part of my everyday work. MelkRadar used Azure DevOps instead of GitHub for its repositories, but underneath it was still Git. During that period I dealt with a lot of branches, merges, conflicts, and all kinds of issues that come with maintaining shared codebases.

Later, I worked more on open-source projects and repositories inside the CS Internship organization.

At some point, something I originally struggled to understand had become something I was teaching other people.

By then, I felt extremely comfortable with Git and GitHub.

After that, I gradually got into GitHub Actions and CI/CD, and that became one of my favorite parts of GitHub.

I loved the idea that I could push my code and have the project automatically run checks and tests, create builds, manage versions, generate changelogs, or publish releases.

GitHub slowly became much more than a place where I stored my code.

My GitHub profile became one of the main places where I presented my work, and I started caring a lot about how my repositories looked and were maintained. Code structure, README files, releases, standards, commits, and the experience someone had when opening one of my projects for the first time all became important to me.

For a while, I was also responsible for creating and managing tasks and issues for a project called CS System. It wasn't a huge project, but it gave me the chance to use GitHub for part of the planning and management process too, not just the code.

Git and GitHub are now tools I rarely have to consciously think about while I'm working. They're simply part of how I build and manage software.

I'm very comfortable with both of them, and I genuinely enjoy working with them.

Especially GitHub.

اولین بار اواخر سال ۲۰۲۲ از طریق برنامه CS Internship با Git و GitHub آشنا شدم.

اوایلش واقعا برام پیچیده بود و خیلی خوب نمی‌فهمیدم دقیقا چه اتفاقی داره می‌افته. Commit چیه، Branch چرا داریم، تغییرات کجا میرن و اصلا چرا باید پروژه‌م رو این شکلی مدیریت کنم.

ولی آروم آروم خودم رو مجبور کردم پروژه‌هام رو به‌جای اینکه فقط روی لپ‌تاپم نگه دارم، روی GitHub هم بذارم.

کم‌کم دستم باهاش گرم شد. بعد با GitHub Desktop آشنا شدم و رابطه‌م با Git تقریبا عوض شد. یه چیزی که قبلا برام گنگ و پیچیده بود، تبدیل شد به چیزی که می‌تونستم خیلی راحت‌تر ببینمش و بفهمم چه اتفاقی داره می‌افته.

حدود یک سال و نیم بیشتر در حد پروژه‌های خودم و CS باهاش کار می‌کردم. Branch می‌ساختم، Commit می‌زدم، تغییرات رو مدیریت می‌کردم و آروم آروم مدل فکری Git برام جا افتاد.

بعد وارد اولین شرکت واقعیم، ملک‌رادار، شدم و اونجا بود که کار کردن واقعی با Git رو دیدم.

دیگه فقط یه main و چندتا Commit نبود. با مدل نام‌گذاری Branchها، Pull Request، Feature Branch، Hotfix، Develop، Production و جریان واقعی توسعه چند پروژه کنار یه تیم آشنا شدم.

مدتی بعد مسئول ریویوی Pull Requestهای تیم فرانت شدم و از اونجا دیگه بخش خیلی بزرگی از کار روزانه‌م شد کار کردن با Git و PRها.

شرکت از Azure DevOps استفاده می‌کرد، ولی زیرش همچنان Git بود. تو اون مدت با تعداد زیادی Branch، Merge، Conflict و مشکلات مختلفی که موقع کار روی Codebaseهای مشترک پیش میاد درگیر شدم.

بعدتر روی پروژه‌های Open Source و ریپازیتوری‌های CS Internship هم بیشتر کار کردم و یه جایی متوجه شدم چیزی که یه زمانی خودم به‌زور می‌فهمیدم، حالا تبدیل شده به چیزی که دارم به بقیه یاد میدم.

از اونجا دیگه خودم رو اوستای Git و GitHub می‌دونستم. :)

بعد کم‌کم وارد دنیای GitHub Actions و CI/CD شدم و اینجا بود که یه بخش جدید از GitHub رو پیدا کردم که واقعا عاشقش شدم.

اینکه Push کنم و بعد سیستم خودش کد رو بررسی کنه، تست‌ها رو اجرا کنه، Build بگیره، Version بزنه، Changelog بسازه یا Release منتشر کنه برام فوق العاده شیرین بود.

کم‌کم GitHub برای من فقط جایی برای نگه داشتن کد نبود.

صفحه GitHubم تبدیل شد به یکی از مهم‌ترین بخش‌های رزومه‌م و جایی که بیشتر از خیلی پلتفرم‌های دیگه براش وقت می‌ذاشتم. نظم Repositoryها، ساختار کد، READMEها، Releaseها، استانداردها، Commitها و اینکه یه پروژه وقتی کسی برای اولین بار واردش میشه چه شکلی به نظر میاد، برام مهم شد.

یه مدت هم مسئول Task و Issue ساختن و مدیریت یه پروژه به اسم CS System شدم. پروژه بزرگی نبود، ولی تجربه جالبی بود که این بار از GitHub فقط برای کد استفاده نکنم و بخشی از برنامه‌ریزی و مدیریت کار پروژه رو هم داخلش انجام بدم.

Git و GitHub الان جزو اون ابزارهایی هستند که موقع کار کردن تقریبا دیگه به خود ابزار فکر نمی‌کنم. فقط بخشی از مدل طبیعی کار کردنم شدند.

خیلی باهاشون راحتم و واقعا دوستشون دارم.

مخصوصا GitHub :)
